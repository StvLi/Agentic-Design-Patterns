# 设计备忘：用 ROS/ROS2 做多 agent 通信中间件

> 状态：**初步想法**，多数条目尚待实验验证。文中标了 `[结论]` / `[假设]` / `[待验证]`，
> 别把假设当结论用。

## 一、动机

在做多智能体系统时，agent 之间的通信目前靠框架内部的 state / 转交 / 工具调用（见
`ch07_notes_communication.md`）。这些机制有两个局限：

1. **都挤在一个进程里**，跨机、跨语言要另外造轮子
2. **state 是 last-write-wins、无历史**，调试时看不到消息流

想法是：**用 ROS 2 的 topic / service / action 做 agent 间的通信层**，用它区分不同
agent 的信息流，并顺带获得记录、观测和实时性能力。

补充动机（具身场景特有）：**ROS 与具身机器人天然适配**，agent 可以直接从同一套
通信层拿到底层信息（图像、关节状态、TF 等），不需要额外搭一条数据通道。

## 二、最重要的一个判断

> **[结论] LLM agent 的实时性瓶颈在推理（秒级），不在消息传输（毫秒级）。**

所以：**用 DDS 优化传输层，几乎不会改善端到端延迟**——95% 以上的时间在等模型返回。

这不否定 ROS 的价值，而是要把它的价值定位到正确的地方（下一节）。
如果把"更实时"当成这套方案的主要卖点，设计重心就会跑偏。

## 三、ROS 真正带来的东西（按价值排序）

| # | 能力 | 对多 agent 系统的意义 |
|---|---|---|
| 1 | **rosbag 记录 + 回放** | 整条消息流可录、可回放调试 —— **我认为收益最大** |
| 2 | **与机器人天然适配** | 图像/关节/TF 在同一套通信层里，agent 不用另接数据通道 |
| 3 | **拓扑可视化**（rqt_graph、topic hz） | "谁在跟谁说话"一眼可见 |
| 4 | **QoS**（reliability / deadline / liveliness） | 能做 agent 掉线检测，HTTP 轮询做不到 |
| 5 | **跨进程/跨机发现**（DDS） | agent 不必挤在一个 Python 进程里 |
| 6 | **共享时间域** | agent 与机器人控制回路用同一个时钟 |

## 四、关于"直接抓取底层信息"的几点考虑

这是具身场景最有价值的一条，但也有几个必须处理的问题：

**[结论] agent 消费不了原始数据流。**
图像/点云要经过 VLM 或编码器转成文本/embedding，才能进模型上下文。
所以"无缝抓取"的实际链路是：**topic 取到 → 转成 agent 能读的形式 → 再进 prompt**，
中间那一步不能省。

**[假设] agent 不该订阅原始高频流。**
相机通常 30Hz，agent 一次决策只用到几帧。让 agent 订阅原始流会带来：
无谓带宽、无谓序列化、以及"拿到哪一帧"的不确定性。
建议改为：**按需快照**（调用一次取一帧）或**事件触发**（变化/异常时才推给 agent）。

**[待验证] QoS 不匹配是个常见坑。**
sensor 类 topic 通常是 `best_effort`；如果 agent 侧写成 `reliable`，会出现
**订阅成功但收不到消息**（ROS 2 典型的静默失败）。接的时候要显式对齐 QoS。

**[待验证] 多模态输入需要时间对齐。**
agent 若要"看着图 + 结合当前关节状态"做判断，这两条流必须取自同一时刻。
ROS 里有 message_filters 这类机制，但要在协议里明确"快照 = 一组对齐的消息"，
否则 agent 拿到的是不同时刻的世界。

## 五、建议的架构：分层，而不是一把梭

**把所有东西都塞进 LLM 回路是最大的坑。** 建议三层：

```
┌─ 快回路（毫秒级，不含 LLM，确定性）─────────────┐
│  传感器 → 状态估计 → 安全校验 → 控制             │  ROS topic / 实时线程
└───────────────┬────────────────────────────────┘
                │ 事件摘要 / 异常 / 对齐快照
                ▼
┌─ 慢回路（秒级，LLM 规划与决策）─────────────────┐
│  agent 编排、工具调用、反思                       │  ROS topic（异步）+ action
└───────────────┬────────────────────────────────┘
                │ 命令（可取消、可超时）
                ▼
┌─ 执行（ROS action）────────────────────────────┐
└────────────────────────────────────────────────┘
```

**实时性由快回路保证，LLM 只负责决策。** 这样"实时"和"智能"各归各位。

## 六、topic / service / action 怎么选

**[结论] 按交互语义分，不要按 agent 类型分。**

| 交互语义 | 用什么 | 例子 |
|---|---|---|
| 单向事件流 / 状态广播 | **topic**（要"当前值"就加 `transient_local`） | agent 上线、任务进度、感知结果 |
| 短请求-响应（毫秒~百毫秒） | **service** | 查参数、取一次状态 |
| **长任务（秒~分钟，要反馈、能取消）** | **action** ✅ | **agent 推理、规划、工具执行** |

最后一行最容易漏：**agent 调用天然是 action，不是 service**。
- 用 service：调用方被卡住，中间没有进度
- 用 topic：拿不到"结果"这个明确返回
- 用 action：goal / feedback / cancel / result —— 正好对上"想很久 + 要进度 + 可能取消"

## 七、三个风险

**① 强类型 schema：优势，但要设计。**
ROS msg 是编译期检查的，这**恰好能治我们前几章反复遇到的病**——"靠字符串名字对齐契约"。
建议定义 `AgentMessage.msg`：
`correlation_id`、`from`、`to`、`intent`、`payload`（JSON 或嵌套 msg）、`deadline`。
等于把第 5 章的 pydantic 校验升级成**跨进程的编译期约定**。

**② state 与 topic 的语义错配。**
框架里的 state 是 last-write-wins、无历史（实测过：并行时撞 key 是竞态）；
topic 是"流"。设计时要明确：**哪个 topic 表示"事件流"，哪个表示"当前值"**。
多个发布者写同一个"当前值"topic，会重现同一个竞态问题。

**③ bridge 会成为单点。**
ADK / CrewAI 的 agent 是**进程内 Python 对象**，接到 ROS 上必须有桥。
桥既是翻译器也是瓶颈和故障点 → **只让一个明确组件做翻译**，
不要让 agent 直接发 ROS 消息。

## 八、边界：什么时候**不**该用

| 场景 | 建议 |
|---|---|
| 所有 agent 在同一进程 | ❌ 用 asyncio 队列，更快更简单，别引入 DDS |
| 跨进程 / 跨机 / 跨语言 | ✅ ROS 划算 |
| 需要和机器人控制回路共享时间域 | ✅ 强烈推荐 |
| 只是想"让多 agent 更快" | ❌ 先量延迟构成，瓶颈大概率在模型 |

## 九、动手前先做的一次测量

**[待验证] 延迟预算。** 拿现成场景测三个数：

```
端到端延迟 = 传输 + 排队 + 【模型推理】 + 后处理
```

- 模型占 **90%+** → 这套协议的价值在**可观测性/可记录/跨机**，优先做 rosbag 和拓扑
- 传输排队占 **30%+** → 确实需要更好的总线，ROS 是对的选择

**这个数字决定设计重心，比先写协议更值得花半天。**
